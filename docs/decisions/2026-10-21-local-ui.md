# 2026-10-21: Local UI as a thin, token-protected view over the store

## Context

The CLI is complete and testable, but the primary task flow — import a trace, label a
failure, run a comparison, add an assertion, export CI config — requires remembering
several commands and reading terminal tables. A UI shortens that loop without adding a
hosted service, a second data model, or a paid dependency.

## Decision

Ship `trace-to-eval serve`: a Python `http.server` process that serves one static
HTML/CSS/JS application from the installed package and a small JSON API over the existing
`CaseStore`.

- **Zero dependencies.** No framework, bundler, or npm install. Assets are package data.
- **Loopback only.** `127.0.0.1` by default; non-loopback binding needs `--allow-remote`
  and is explicitly unauthenticated.
- **Token-gated mutations.** A per-process CSRF token is injected into the page and
  required on every mutating request, together with a same-origin check, an `application/json`
  content type, and a `Host` allowlist.
- **One runner.** `POST /api/run` calls the same `run_replay` path as the CLI with the fake
  provider. The UI cannot spend money: live adapters stay behind `--allow-live` in the CLI.
- **No new storage.** Views read the store directly; nothing is cached, duplicated, or
  written outside the SQLite file.
- **Generated CI config, not stored config.** The CI view renders a config file, workflow,
  and command from resolved thresholds. It never writes those files, so the repository
  stays the single source of truth and a stale UI cannot silently change a build.

## Alternatives considered

- **A hosted dashboard.** Rejected: requires accounts, a database service, and a paid plan,
  violating the $0 constraint and the local-first privacy promise.
- **A React/Vite frontend.** Rejected: adds a build step and a node toolchain to a
  zero-dependency Python package for six views.
- **A TUI.** Kept as a future option; it would not exercise the CI/export flow or the
  responsive layouts the UI/UX plan requires.

## Consequences

- The UI must be verified in a real browser (axe, keyboard, overflow, screenshots) because
  there is no component test framework.
- API changes are contract changes: `tests/integration/test_ui_server.py` covers the HTTP
  surface, and `tests/unit/test_server_payloads.py` covers presentation helpers.
- The static assets ship with the package, so a release must include `web/` package data.
